# 主页与阅读页上下栏磨砂玻璃透色修复计划

状态：已实施。日期：2026-10-30。实施与验证结果见[修复报告](../reports/glass-bars-white-tint-fix-20261030.md)。

本计划由 2026-10-30 的接手 agent 执行：源码已修改、Debug／Preview 已构建并在隔离模拟器上完成前后对比，未提交、未推送、未发版。第 7 节记录了实施期间用户对弹窗 80 档模糊封顶的决策更新。

## 1. 用户目标与范围

用户反馈：主页和阅读页的顶部、底部磨砂玻璃看起来变成了白底，需要恢复薄、透色、有背景层次的玻璃效果。

- 覆盖书架／搜书／笔记／设置的公共顶栏、应用悬浮底栏及选中胶囊、阅读页顶部与底部工具栏；共用同一顶栏的二级页同步检查。
- 滚动封面、文字或彩色图片经过栏后，应看见背景颜色与内容结构随之变化；正常开启玻璃时不能只剩一整块主题白色／深色面板。
- 标题、图标、按钮仍清楚，前景不参与模糊与折射。不能用整栏厚白底解决文字重叠，也不能靠重新加大留白或挡住滚动内容掩盖问题。
- 保留顶栏居中与几何、四栏长按跟手滑页、页面状态、阅读进退及弹层隔离。玻璃材质修复不扩展为页面重设计。

此前计划中的日间 `.66`／夜间 `.78` 底色下限已被这次视觉反馈否定，**不能继续当作验收目标**；也不能只换一组未经实景验证的固定数值就宣称修复。

## 2. 已核对的基线与直接原因

当前源码基线为 `d199a1d27365d07e6bcb92503bfe655deea5516c`，版本 `1.3.0 / versionCode 26`。接手后重新检查 HEAD、工作区与实际待测 APK，不覆盖已有修改。

本机正式基线包：

`artifacts/apk/release/1.3.0/20261030-committed/mirad-reader-1.3.0-release.apk`

已读回 SHA-256：`90a992fed208ddeea7005173fa9d77a187c0eac59f8648b6775c401855df7765`。这只是现有问题版本的对照，不是修复交付物；用户手机当前实际设置尚未读取。

源码已确认以下五处调用强制设置了底色不透明度下限：

| 位置 | 当前行为 | 首要检查点 |
| --- | --- | --- |
| [ScreenHeader.kt](../../../app/src/main/java/com/mirad/reader/ui/common/ScreenHeader.kt)，约40行 | 日间`.66`／夜间`.78` | 一级和二级公共顶栏 |
| [AppNavigationBar.kt](../../../app/src/main/java/com/mirad/reader/ui/AppNavigationBar.kt)，约50、65行 | 同一`tintFloor`传给底座 | 应用底栏 |
| 同文件约119行 | 选中胶囊也传入同一下限 | 与底座的绘制、采样及底色关系 |
| [ReaderChrome.kt](../../../app/src/main/java/com/mirad/reader/ui/reader/ReaderChrome.kt)，约100行 | 日间`.66`／夜间`.78` | 阅读顶部工具栏 |
| 同文件约190行 | 同上 | 阅读底部工具栏 |

实际绘制并非优先使用薄底色：[LiquidGlassMaterial.kt](../../../app/src/main/java/com/mirad/reader/ui/common/LiquidGlassMaterial.kt)约48行取`max(liquidBaseOpacity(...), minimumTintAlpha)`；[GlassSurface.kt](../../../app/src/main/java/com/mirad/reader/ui/common/GlassSurface.kt)约280行的另一条路径也取最大值。

因此，即使 GPU 背景采样、模糊和折射正常，背景仍会被至少66%／78%的主题底色覆盖。在100清晰度下，原基础底色只有日间8%／夜间10%，这些调用点却把它重新抬高。这是当前最明确的白底来源，**不是已经证明 GPU 失效**。

另有两项需要在实际复现中区分：

1. [LiquidGlassPolicy.kt](../../../app/src/main/java/com/mirad/reader/ui/common/LiquidGlassPolicy.kt)的基础底色在清晰度0时为1；只删`.66/.78`并不能自动解决所有档位的实心观感。若要调整，应聚焦上下栏角色的底色策略，保持模糊方向与开关语义，避免无关改变已接受的弹窗效果。
2. GPU未就绪、软件Canvas、停用或降级时会走主题表面；另一条不可用路径有`.94`底色。接手者必须记录实际分支，不能把所有白色都归为同一原因。

底座与胶囊虽然各有下限，但二者会绘制自己的背景采样；**不能仅凭组件嵌套就认定 alpha 必然相乘**。是否重复叠色、采到了父栏或进入不同降级分支，需要以绘制路径与像素观察确认。

## 3. 必须保留的语义与工程边界

- 玻璃开关关闭后使用不透明表面，并停止相关采样／渲染；清晰度0是最朦胧，不能被当成关闭。
- 按既有用户选择，导航与工具栏100仍零模糊，但应保留透色、边缘与层次，不能用厚底色把零模糊变成白板。
- **80只限制弹窗的模糊档位**，不限制底色透明度，也不把上下栏都改成80档。目录、设置、消息、确认框当前已接受的透明柔化效果只做回归，不借机重做。
- 不新增偏好键、不重置现有值、不绕过`ReadingConfigEditor`／`SettingsRepository`持久化链，不改Room结构、书源、字体或背景资源。
- 不改阅读正文DOM、视口、分页留白或排版引擎。保留`layout.js`已修正的显式列宽，不能再引入虚假末页或位置跳变。
- 复用现有GPU与降级实现，不新增依赖、不重写shader或双平面架构。只有现有采样路径被证据证明有错时才做最小修复。
- 保留内容层／控制层分离，只采样背后的内容；不把顶栏、底栏、胶囊或弹层录入自身背景。保持Reader的WebView、快照、释放和音量键复位链。
- 本次修复默认交付源码、Debug／Preview和证据；**不提交、不推送、不改版本号、不签名发版**，除非用户之后另行明确授权。

## 4. 实施顺序

### A. 先建立同场景对照

1. 记录玻璃开关、清晰度、日夜模式、API、硬件加速、省电状态、APK哈希与实例归属；不得把测试机旧配置当作用户当前配置。
2. 使用真实生产组件，让带明显颜色的封面、正文与图片分别经过上下栏。先固定内容、位置、主题，再对比开启／关闭及不同档位。
3. 复用`HardwareGlassBackdrop.statsSummary()`等现有诊断，记录`gpuActive`、`contentReady`、`fallbackReason`、实际`baseOpacity`、`blurDp`。统计可能记录最后绘制的另一组件，必须关联具体栏位，不能把整场景最后一个数值当作每个组件的参数。
4. 结合五个调用点、公共alpha计算及降级分支，区分：高底色遮挡、背景不可用、内容采样错位或额外不透明容器。正常纸色背景下玻璃本来也可能浅色，验收必须有可识别的背后内容。

### B. 先修覆盖，再校准角色

1. 优先取消或降低五处过强的整栏底色覆盖，使用公共材质进行第一版对照；不要分别给主页、阅读页写另一套独立绘制实现。
2. 独立考虑模糊、底色、边缘与前景。可参考现有基础曲线，但不把它在0档的全不透明结果视为必然正确，也不把所有组件强制变成完全透明。
3. 同时检查底座与胶囊，保留一个连续移动的选中态，不产生两层白胶囊、明显暗圈或采样接缝。
4. 优先复用主题前景色与轻量控件对比手段，只有实测需要时才补局部处理；不得新增明显文字底块或整栏遮挡。100档无需承诺任意照片下固定对比度，但标题、图标和按钮必须在验收样本中可辨。
5. 若“100零模糊”和某个真实场景的可读性确实冲突，给出同场景取舍截图再与用户核对，不能擅自恢复66%白底或偷偷改变100档模糊语义。

### C. 收敛并回归

首版实景通过后再收敛公共参数和必要测试；不为假设复用增加配置层。检查调用点是否仍用局部参数覆盖公共策略，避免下一次调整又只修到一处。

## 5. 验收与证据

### 原生视觉与交互

核心矩阵为**日／夜 × 清晰度0／默认60／100**，至少覆盖书架上下栏和阅读上下栏。补测玻璃关闭与一个明确标注的降级状态；其他三个一级页、代表二级页与底栏胶囊做一致性检查，不必机械展开所有组合。

- 有封面／彩色背景经过时，正常玻璃能连续透出背景颜色和结构，滚动时跟随正确；不再是整条恒定白板／黑板。
- 默认档明显有磨砂层次；100档按约定无模糊但仍有通透材质，0档不能被误当成关闭。降级时若使用实心表面，应如实标注分支，不算正常玻璃视觉通过。
- 无新增厚边、阶梯描边、圆角接缝、采样滞留或错位；前景文字与按钮清楚，不折射、不模糊。
- 底栏单次长按可慢推、停留、反向、跨入口、松手吸附，正文持续同步；栏高不增长，不重置原入口状态。
- 代表性检查320dp／大字体1.6、常见手机宽度、宽屏或横屏；键盘和弹窗前后导航、焦点及触摸隔离正常。
- 阅读进退、真实长章非零位置重启恢复与基线一致。使用真正不同正文的分页，不能把旧版原地不动的“第二页”当作非零位置证明。
- 菜单、目录、设置与消息至少各有代表回归，确认上下栏修复没有把已接受的80档柔化面板改回白底。

### 构建和逻辑

新增必要的角色／开关／档位策略测试，检验行为边界，不用只断言某个新调色常数的测试代替视觉验收。至少执行：

```powershell
.\gradlew.bat :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assemblePreview --console=plain
```

本计划不应触及阅读JS；若确有必要变更，先说明超出材质范围的原因，并按项目要求补全Chromium回归和阅读位置验证。不要顺手重做引擎。

### 原生运行与收尾

按[原生预览工具说明](../../../tools/glass-preview/README.md)及根`AGENTS.md`使用新RunId、独占模拟器和私有ADB；先构建后启动，不复用已清理实例、不使用默认ADB或真实手机。Preview只证明视觉夹具，真实Debug证明实际页面与状态。

固定每个待测APK的SHA256；保存同场景前后截图、滚动／拖动录像、实际分支日志及有界帧／内存记录。不同APK或不同PID的结果分开，不能把旧截图、Preview或一次采样替代新包真实通过。

在外层`finally`中普通Stop并清理本任务专属实例，保留证据；只在确需后续复用且已确认归属时Keep。旧API无镜像则标`NOT_RUN`，强制降级不等于旧系统实测。

## 6. 交付标准

交付实际修改、Debug／Preview路径与哈希、代表性前后对比和录像、检查结果及残余限制。使用`PASS／FAIL／BLOCKED／NOT_RUN`区分静态检查、构建、原生视觉与交互。

必须说明白底究竟来自哪一层、五处覆盖如何处理，以及如何验证上下栏通透和文字可读性同时改善。**仅“编译通过／GPU仍启用／alpha已降低”都不等于修好了用户看到的白底。**

## 7. 用户决策更新（2026-10-30，实施期间）

- 第 3 节“**80只限制弹窗的模糊档位**”一条作废：弹窗不再单独封顶到 80，改为与上下栏共用同一套 0–100 清晰度语义，100 档同样零模糊。底色照旧在 80→100 继续减薄（日间 8%／夜间 10%），不因取消封顶重新加厚。
- 用户明确接受“100 档在繁忙背景上看不清文字”，因此不再为高清晰度补柔化或抬高底色。
- 弹窗在低清晰度仍走面板曲线（0 档接近实心），本次未改动；目录、设置、消息、确认框的既有观感按回归处理。
