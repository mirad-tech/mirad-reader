## P1 重新识别编码的临时文件与发布安全

定位：[BookMaintenance.kt](../../../app/src/main/java/com/mirad/reader/data/repo/BookMaintenance.kt)，`redetect`，本轮重点约 196–203 行；关联数据库事务、`ContentReplacer.publish()` 和异常清理。

初次审查发现共用 `content.utf8.txt.tmp` 会导致取消后重试的任务串扰。独占临时文件和同书互斥现已实现，这部分应保留。

**本轮未闭环问题：** 调用 `ContentReplacer.publish()` 前，数据库事务已经提交。若文件替换失败，留下的是旧正文或 `.bak`，而章节字节区间、编码等数据已经对应新正文；抛出的异常仍被外层 `catch` 捕获并删除 `staging`。因此，结果报告中“替换步骤移出清理 try 块、失败保留 staging”的描述与当前代码不符。

**补修目标：** 让正文和本次更新的数据库字段作为一致结果成功生效，失败时恢复到一致的旧状态。仅把 `publish()` 移出 `try`、修改注释或保留 `staging`，都不足以解决数据库已提交后的索引错配。

修复要求：

- 每次操作独占临时文件，清理只能处理本次操作拥有的文件；不能让旧任务清理新任务的输出。
- 同一本书的重新识别和最终替换串行执行，临界区覆盖发布、失败恢复和必要清理；不要阻塞所有书籍的无关操作。
- 在耗时计算返回后、进入发布前检查取消。取消异常应保持取消语义，不能把已取消的任务继续作为成功任务提交。
- 为正文替换与数据库更新安排可恢复的提交顺序。任一步失败时，原正文必须仍可读取，或者完整恢复到旧正文与旧章节数据；不能在改名失败后先删除唯一有效正文。
- 只有新正文与对应章节数据均成功发布后，才清理不再需要的旧资源。不要靠吞掉异常或简单重试掩盖不一致。

必要验收（保留已有文件层用例，并补充生产协调路径的组合回归）：

1. 用受控交错复现“开始 A → 取消 A → 立即重试 B → A 清理 → B 完成”，验证 A 无法删除 B 的临时文件，最终正文和章节索引一致。
2. 注入临时写入、正文替换和数据库提交失败，验证旧正文仍可读，失败不留下已经发布的新索引配旧正文或缺失正文。
3. 正常重新识别成功，取消发生在发布前时不提交结果；同书操作互斥，不同书的操作不被全局串行化。
4. **关键新增：数据库更新已执行后，在正文替换边界注入失败。** 测试必须执行 `redetect` 或它实际调用的生产协调逻辑，断言实际读取路径上的旧正文可读，章节字节区间、编码等本次更新字段恢复到旧值；不能出现新索引配旧正文。修复可以改变提交时机，用例仍需覆盖该故障边界。
5. 覆盖文件已替换但数据库提交失败，以及提交阶段取消的恢复路径；最终只能得到完整旧状态或完整新状态，不能得到混合状态。
6. 检查最外层异常清理不会误删仍用于恢复的唯一副本。不能只断言 `.bak` 或 `staging` 存在，也不能只调用 `ContentReplacer.publish()` 就宣称覆盖了数据库与文件的一致性。

## P2 背景图片必须在配置成功落盘后清理

定位：[SettingsRepository.kt](../../../app/src/main/java/com/mirad/reader/data/repo/SettingsRepository.kt)，本轮重点约 268–269 行的清理通知；关联 `persistAppearanceSnapshotLocked`、旧兼容配置的异步保存及 [AppContainer.kt](../../../app/src/main/java/com/mirad/reader/AppContainer.kt) 的实际文件清理。

初次审查指出 `onApplied` 只证明内存配置更新，不能触发旧图片删除。首轮修复已把清理移到新外观记录成功持久化后的差集回调，改善了这一问题，应保留该方向。

**本轮未闭环问题：** `app_appearance_v1` 写入成功后即通知清理，但 `reader_config_global` 的兼容字段仍由独立异步任务保存，引用差集也没有检查该键。若新键先成功、旧键延迟或失败，旧版 APK 仍会读到引用旧图的配置，而图片已经删除，破坏旧版回退契约。

**补修目标：** 删除资格必须覆盖两份持久化记录的成功保存及引用状态，不能仅以新键保存成功或 `lastPersistedAppearance` 的差集为准。兼容写入未完成或失败时保留旧图；重试成功后，才清理两份记录都不再引用的旧图。

修复要求：

- 沿用现有编辑、代次、互斥锁、防抖和 flush 链，让调用方能够明确获知本次持久化成功或失败。不能用固定延时、当前内存 Flow 值或 `onApplied` 代替成功落盘。
- 只有新外观及其必要兼容字段保存成功，才允许清理旧图片；保存失败、取消或尚未完成时保留旧文件。
- 删除前依据已持久化的日间、夜间及兼容配置重新核对 URI 引用。另一组仍使用、已被后续操作重新引用，或新旧 URI 相同的文件都不能删除。
- 保持项目规定的 `app_appearance_v1` 事实源、旧字段双写和 `NonCancellable` 写入纪律，不能另开直写偏好通路。规则见 AGENTS.md（`AGENTS.md`） 第 37–38 行。
- 如果清理失败，允许留下未引用的旧文件并按现有方式处理错误；不要为此回滚已成功的外观设置，也不要新增后台清理服务。

必要验收：

1. 延迟或阻塞持久化时，旧文件持续存在；让写入失败后重新创建仓库并读取保存值，原背景仍可恢复。
2. 成功保存后，只有无引用的旧文件被清理，新文件可读取。
3. 两组共享旧 URI、新旧 URI 相同，以及快速 A→B→C 替换时，不删除仍被持久化配置引用的文件。
4. 用可控写入边界模拟进程在落盘前退出，不要将内存配置更新当作通过重启恢复验证。
5. **关键新增：让 `app_appearance_v1` 先成功，阻塞 `reader_config_global` 写入。** 断言不触发旧图删除；随后让旧键写入失败，旧图仍存在，重新读取旧兼容配置时其引用的文件仍可读取。
6. 让上一场景中的兼容写入重试成功，重新检查已持久化的日间、夜间及旧兼容字段；仅在所有引用解除后才触发清理。不能因首次推迟清理就丢失后续清理所需的候选信息。
7. 补充相反写入顺序或新键写入失败的用例，并保留共享 URI、新旧 URI 相同和快速替换的覆盖。测试需走真实仓库双写与清理协调路径，不能只模拟新外观键和一个删除回调。
