## 3 剩余五项的修复与验收

### S1 在途采样后的末次更新必达

定位：`ui/common/GlassSurface.kt` 的 `notifySourceChanged`、`requestSnapshot`、`scheduleTrailingOnScope`。审查基线中，当前采样在 `finally` 请求安排尾帧，但 `trailingJob` 仍指向正在结束的自己，`isActive` 判断使补采直接返回。复现结果为采样 1 次、发布帧 1，最后请求的帧 2 在等待 450ms 后仍未处理。

修复范围：区分正在采样与已经安排的冷却任务，使当前任务结束不会阻止下一次必要补采。合并中间变化，保留最新事件，不要求逐帧执行。仍保持单源最多一个任务在途、共享快照最高 10 次/秒、同一区域分析最高 5 次/秒；不能通过并发增加、永久轮询或恢复绘制自增状态绕过问题。取消、0%、后台和旧代次结束不能清掉新代次的任务状态或复活旧结果。

验收：保留真实协程挂起场景——开始帧 A 采样，挂起期间输入 B，再恢复 A；此后不输入任何新事件，也必须按节流规则补采并发布 B。扩展 A 在途时连续输入 B/C/D、冷却窗口最后一次事件、多个消费者、取消/切 0 后恢复；最终帧正确，任务并发数不超过 1。原生持续绘制与停止后的末帧对照、空闲计数均通过。允许适配新的内部接口，但不能用不发生挂起的同步夹具替代在途测试。

### S2 用可靠的画面一致性判断去重

定位：`ui/common/GlassSurface.kt` 的 `computeBitmapFingerprint` 和相同指纹时跳过发布的分支。审查夹具在 128×128 图片中改变一条全宽 8px 横带，1024/16384 像素变化，两个指纹仍相同，随后新快照和分析被跳过。

修复范围：判定整帧相同必须有完整有界像素一致性或可靠脏区证据，稀疏抽点不能作为唯一依据。复用已有有界位图和变更通知，以最小实现完成可靠比较；比较成本和资源存活仍受现有尺寸、频率限制。几何、来源或代次变化也须正确处理。重复相同画面应继续去重，不能靠无条件持续发布重新产生重绘循环。

验收：保留横带像素样例，增加竖带、局部小块、字符/图片局部变化、尺寸变化与完全相同帧。断言真实内容变化会到达共享快照及对应局部分析，相同帧不重复发布；跨窗口原生画面能看到变化。旧探针直接比较私有哈希值，本轮应迁移为发布行为断言：可以更换实现或保留辅助哈希，但不能只修改样例、常量或抽样网格来让旧断言通过。

### S3 保留实际 RGB 颜色并验证合成结果

定位：`ui/common/GlassPolicy.kt` 的背景采样、`meetsThemeContrastAtAlpha` 及参数求解。审查基线把背景亮度转换成一个 `bgSrgb` 灰度值，并同时用于 R/G/B。纯蓝 `#0000FF`、浅色面板、100% 偏好时得到不透明度 0.697426，副文字 `#4C554F` 按实际 RGB 通道合成仅为 3.805553:1。

修复范围：保留局部实际 RGB 样本，或采用对实际 RGB 成立的保守界；亮度分位数只能承担统计用途，不能重建为灰色后冒充原背景。明确一次线性化边界、实际渲染颜色空间及底色/高光/前景的合成顺序。校验真实主题中受保护的普通及次要文字；若保留多个合成模型，全部输入真实颜色并说明用途。必要的保护仍需及时生效，释放可平滑，不回写用户百分比。本项与 T1 一起设计，减少误判和过度全局保护。

验收：保留纯蓝反例及已通过的深色灰底、浅色无高光反例；覆盖红/绿/蓝、混合饱和色、低饱和色、黑白灰与纹理，深浅主题、工具栏/面板、0/25/60/100%，以及高光顶部/中部/底部。用独立公式计算，并用受控背景的原生像素验证实际合成假设；受测普通非禁用文字至少 4.5:1。记录颜色、参数、采样位置和最小比值，不能只挑有利高光或合成模型。若不能原生验证，应明确列为未验证，不能写“已保证”。

### S4 让保存失败可见并可恢复

定位：`data/repo/SettingsRepository.kt` 的 `glassSaveFailed`、`AppRoot` 外观状态接线与 `AppearanceSettings`。审查时只有仓库和单测引用失败状态，页面没有消费它。

修复范围：通过实际应用状态/controller 将失败传到全局设置与阅读设置两个入口，沿用现有错误反馈形式给出必要提示和重试操作。失败时保留用户最新选择及待保存值，不能伪装成功或回退显示；重试应保存最新值，旧写入的成功/失败回调不能覆盖新状态。成功后清除相应错误，避免重复弹出同一失败。保留已修好的应用级保存、松手/离页提交与两入口同步，不扩展到普通阅读配置或改变 B1。

验收：对生产保存链注入“失败后成功”、连续失败、失败后再次拖动/恢复默认、离页再进入及两入口切换。验证提示确实显示、重试可操作、最终写入的是最新值、成功后提示恢复，失败不会吞掉待保存内容。仓库测试使用已有内存 DAO；原生预览通过同一错误状态接口验证提示与恢复交互，不创建业务数据库。仅断言 `glassSaveFailed == true` 不算完成 UI 验收。

### S5 先核对服务归属再启动或清理

定位：`tools/glass-preview/Run-FixVerification.ps1` 的无条件 `adb -P 5049 kill-server`，以及现有驱动的实例身份检查。

修复范围：移除无归属检查的停止动作，在启动、失败清理和正常退出前统一核对 RunId、实例文件、端口监听 PID、进程命令行及其归属。端口空闲时正常启动；只有确认属于当前任务的服务才可复用或停止。归属不明、PID/命令不匹配、元数据过期或端口被其他实例占用时，保留现场并明确失败，不自动终止。检查应覆盖 `finally`，不能在前置校验失败后又无条件清理服务。

继续使用专用端口和明确的模拟器 serial；不得查询默认 `adb devices`、启动/停止默认 ADB 服务或连接用户手机。原交付执行记录出现过默认 ADB 查询和停止，本轮必须避免重复；不能凭报告声明推断这些操作没有影响。

验收：用命令执行记录/测试替身验证归属不匹配时不会发出 stop/kill 或默认 ADB 命令；必要的集成负向检查只使用本轮自行创建的隔离监听器，不能借用户服务测试。覆盖空闲端口、当前实例、其他实例、旧 PID 元数据和异常退出；负向检查须非零返回且原监听者仍存活，正向流程结束只关闭本次实例，并确认相关端口释放。保留已有菜单 36 轮断言、错误场景拒绝和固定 APK 机制。

## 4 T1 用户新增需求 100% 时明显更透明

用户明确反馈“磨砂玻璃透明度不够，想让 100% 更透明”。这是本轮新增的效果要求，与 S3 同步设计。保留磨砂细节、轻量边缘、纸墨配色及前景文字清晰度；0% 仍是不透明底色，默认值仍为 60%，两个入口继续控制同一个应用级值。

实施要求：

1. 100% 必须带来实际可见的更强透底效果，减轻当前偏厚的整块着色/白色蒙层和全局保护叠加。基础全局着色在高透明度端应趋于最低值，固定的面板/深色厚度补偿也须随高端透明度合理减弱，不能只改变显示百分比或文案。
2. 先纠正采样、颜色计算与冗余保护造成的误判；仍需文字保护时，将它限制到实际需要的文字承载区域或最小必要范围，复用现有样式能力。不能由一个不相关的极端像素把整块玻璃长期抬成高不透明度，也不能靠降低文字透明度、模糊前景或新增说明卡片解决。
3. 保持受测普通文字 4.5:1 目标。保护计算以真实文字位置的合成结果为依据；普通背景下 100% 应明显比 60% 通透。极端背景需要的额外保护应有对应区域和计算证据，其余玻璃区域仍体现高透明偏好。
4. 全局设置影响所有既有玻璃表面，不新增单页特例或新配置键，不改阅读正文、弹层遮罩与图标的透明度。拖动保持实时响应和稳定过渡，不造成重排、进度变化或空闲持续采样。

验收：先记录当前工作区的 100% 效果作为本轮视觉基线。使用同设备、同内容、同位置、同主题和相同背景，提供“修复前 100% / 修复后 100%”及“修复后 60% / 100%”原生对照；同时记录实际全局遮罩、局部保护和模糊参数。覆盖书架顶栏、阅读上下栏、菜单和底部面板，深浅主题及带颜色/图片的背景。新 100% 下背景轮廓与色彩更清楚、整块蒙层更轻，变化必须同时有画面和参数证据；文字可读性仍按 S3 验证。单纯降低名义 alpha、改截图后处理或只给一张效果图不能关闭 T1。

## 7 交付与独立验收

交付逐项说明 S1–S5/T1 的当前状态、最小修改、生产代码位置、测试输入、命令与退出码、结果和证据路径，并单列已通过基线是否回归。提供实际 diff、最终源文件及三类构建 SHA-256，原生材料关联实际安装的 APK。同步更新交付说明中的真实状态，不把实施方自测写成独立审核结论。

必须明确：哪些只是函数或内存夹具检查，哪些完成原生画面/交互验证，以及完整按钮矩阵、彩色背景像素验证、旧系统、真实存储和手机等尚未覆盖的范围。不能仅以“没有崩溃”、单测总数、截图数量或构建成功认定完成。

修复 agent 实现与自测后停止。只有五项剩余问题有可复验的关闭证据、T1 的更通透效果和清晰度均达标、已经通过的修复无回归，才提请本对话中的审核 agent 独立验收；仍有阻塞或必要证据缺失时维持 `REQUEST_CHANGES`。
